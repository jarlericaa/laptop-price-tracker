# Top 100 eligible mapped Shopee variations (owner decision, 2026-11-03)

> **Update (same day): union of both months.** The pool is no longer limited to variations with an MTD
> record: eligible variations present in M-1 *or* MTD rank (section "Selection universe: both months"
> below). The sections "Why only 53" and "Offline validation" describe the result under the earlier
> MTD-required rule; the audit now reproduces those numbers as the *earlier-rule* column.

The Top 100 now contains **only eligible Shopee variations with a verified configuration mapping**.
This supersedes the 2026-10-27 rule that let unmapped or untrusted variations enter the list as
`CONFIGURATION_REVIEW_PENDING` rows ([SHOPEE_VARIATION_GRAIN_2026-10-27.md](SHOPEE_VARIATION_GRAIN_2026-10-27.md)
still describes the grain, prices, contexts, reports and publisher, all unchanged). Implemented
and validated offline; nothing was published, committed or written to Sheets, and no live
discovery was run.

## Selection rules

1. Read the full eligible variation ranking (Phase 1, unchanged) and the current `SOURCE_MODEL_MAP`
   and `TARGET_MASTER`. The catalog is computed from the inputs each run; previously published
   mapping-status cells are never a source of truth.
2. Resolve every eligible variation's mapping. A variation is `MAPPED_VERIFIED` only when its
   source model ID resolves to exactly one `ACTIVE`, complete `CONFIGURATION` target accepted by the
   existing validator (`_target_issue`, which applies the legacy `LISTING_ONLY` tracking-mode rule
   and the `cpu_model`/`cpu_series` consistency rule), with no open target-level or source-level
   identity-register conflict, and the model ID is tied to one shop/item identity.
3. Keep only `MAPPED_VERIFIED` variations. **That filter runs before the 100-row limit.**
4. Rank that qualifying pool by the Phase 1 metric (each variation's own `ranking_gmv_usd`, M-1 +
   MTD), ties on MTD GMV then `model_id`.
5. Select the first 100. A lower-ranked qualifying variation therefore fills the place of an
   excluded one; the earlier selection is not merely thinned.

`MATCH_REVIEW` completion, retailer coverage and a successful retailer fetch never gate selection
(`build_variation_ranking` takes no MATCH_REVIEW and no retailer data). If fewer than 100 qualify,
the list holds the true count and states the shortfall and its reason; it is never padded with
unmapped or duplicate variations.

## Selection universe: both months (owner decision, 2026-11-03, later the same day)

Select the top 100 eligible Shopee variations with valid configuration mappings that appear in **either
M-1 or MTD**, ranked by the established M-1 + MTD GMV metric. This supersedes any requirement that a
variation have an MTD record.

- **Pool.** `ranking.rank_eligible_models` keeps `ELIGIBLE` models present in M-1 or MTD (Phase 1 already
  applies eligibility, quarantine and the content-based duplicate decisions). Phase 1 now also writes
  `present_in_m_minus_1`, `m_minus_1_status`, `mtd_status`, `price_period_month`, `price_record_date`,
  `price_basis`, `m_minus_1_price_values` (appended; earlier columns are unchanged). Ranking order and the
  deterministic tie-break are unchanged.
- **A missing month is not an observed zero.** The flags are kept on every row; a missing month adds `0` to
  `ranking_gmv_usd` only as labelled arithmetic (`NO_RECORD_TREATED_AS_ZERO`, stated in `rank_metric_scope`
  and as a note on the Sheets GMV cell). It is never evidence that the listing was inactive.
- **Price.** The variation's own latest valid price: the MTD record's, else the M-1 record's. A price from
  an MTD record is dated by the sales extract; a price from the M-1 record is dated by that monthly source
  record (`grass_date`, e.g. 2026-10-01; the exact snapshot time within the month is unknown) with
  `shopee_price_date_basis = M_MINUS_1_RECORD_DATE`, and shows `SNAPSHOT_PRICE_STALE` beyond seven days
  before the cutoff. It is never relabelled as an observation of the later month, no other seller's price is
  used, several prices in the supplying month stay `PRICE_CONFLICT` (no fallback to the older month), and a
  missing price never removes a qualifying variation. The legacy configuration layer does not date an M-1
  price with the extract date (`PRICE_FROM_M_MINUS_1_RECORD`).
- **Unchanged.** Mappings from fresh `SOURCE_MODEL_MAP` / `TARGET_MASTER`, the existing validator and
  `LISTING_ONLY` rule, the qualifying-mapping filter before the 100-row limit, distinct seller variations kept
  separate, no `MATCH_REVIEW` / retailer-coverage / MTD-price requirement, honest shortfall.
- **Counts.** The summary and audit report eligible, qualifying and selected variations in M-1, in MTD, in
  both, in each month only, and their union (`eligible_union`, `qualifying_m_minus_1_only`, ...).
- **Result (2026-11-03 data, fresh catalog).** 1,571 eligible variations (1,554 with an M-1 record, 187 with
  an MTD record, 170 in both, 1,384 M-1 only, 17 MTD only); 205 map to a target; 188 qualify (listing-only 12
  and CPU-model-conflicted 5 removed); the first 100 are selected across 59 contexts, 61 of them with an
  M-1 price and no MTD record. The selection audit reproduces the earlier findings from the run's own rows:
  of 62 mapped variations present in MTD, 4 CPU-conflicted and 5 listing-only leave **53** under the earlier
  rule; mapped IDs with an October record and no November record are **168** (143 eligible variations plus 25
  that Phase 1 holds in eligibility review), and 246 further mapped IDs have no Phase 1 record in either
  month.

`build_variation_reports` and `publish_variation_prices.py` refuse a list or run summary built

## Why only 53: the investigation (2026-11-03)

The 187-row pool and the 53 qualifying rows are correct under the established policies; the
shortfall is an early-month effect of the MTD rule plus the unmapped listings, not a defect.

- **Where 187 comes from.** Phase 1 run `20261103T133451+0800`: 26,683 raw rows (26,662 analysed
  after the 21 conflicting duplicate keys were resolved by the standing keep-latest-row rule), 2,680
  rows in M-1 2026-10, **292 rows in MTD 2026-11** (292 models active in November). 1,571 models are
  `ELIGIBLE` over all periods; the ranking keeps those *present in MTD* (DECISIONS.md: "Only eligible
  models present in MTD may rank"): **187**. The other 1,384 eligible models have no November sales
  yet (the month is three days old).
- **Why earlier pools were larger.** On 2026-10-22, 10-26 and 10-27 the MTD month was October with
  2,136 to 2,382 MTD-active models, so the pools were 1,251, 1,357 and 1,387 rows. Re-evaluated under
  today's catalog, the 10-27 pool has 168 verified variations (100 selected, no shortfall) and the
  10-22 pool 157. Nothing was rebuilt from published cells.
- **Checks that found nothing wrong.** No premature limit (53 < 100, the limit never binds; the audit
  recomputes qualification and checks the selection is the first 100 of the qualifying pool). Inputs
  are complete (every pool row is `ELIGIBLE` and in MTD, unique `source_key` and `model_id`). No
  identifier conversion problem (every ID is a digit string; no unmapped ID equals a mapped one after
  trimming, `.0` or leading zeros). No review gate (`MATCH_REVIEW` is not an input to selection). The
  catalog is current (below).
- **Arithmetic.** 476 mapped source IDs: 62 are in this period's pool, 414 are not (407 of those with
  an active, non-listing-only target: 389 have no November sales or are absent, 25 are in the Phase 1
  eligibility review). Of the 62 in the pool, 5 are `LISTING_ONLY` and 4 have a target whose `cpu_model`
  contradicts its series, leaving **53**. The remaining 125 of the 187 are unmapped.
- **Owner options, not implemented** (the established period policy is preserved): early in a month
  the MTD-presence rule discards the mapped variations that sold in M-1 but not yet in MTD, up to 389
  mapped IDs today. Whether M-1 sales alone may qualify for the first days of a month is an owner
  decision.

## Selected variation takes precedence (`variation_specs.py`)

A mapped variation is compared with its target using only what the **selected variation itself**
states. The variation name is read first; the parent title fills a field only when the variation says
nothing about it and the parent states exactly one value; a parent listing options ("Intel
i7/i5/i3", "4GB-16GB RAM", "Core i7 - i5") applies to no one variation and is never a conflict. The
first CPU of a multi-option title is never taken, no sibling variation is read, ranges and unlabeled
capacity pairs ("8G-256GB", "16+512") stay unknown, and unknown is never filled in or a conflict.
Compared fields: `cpu_series` (series level; no exact CPU SKU is required), `screen_size_in` (only a
difference of an inch or more), `ram_capacity_gb`, `storage_capacity_gb`.

A real disagreement is never ignored: it names the field, both values, whether it came from the
variation or the parent, and the quoted text (`variation_spec_conflicts` column,
`variation_spec_conflicts.csv`, comparison detail). A mapped row that disagrees with its target is
excluded as `VARIATION_TARGET_SPEC_CONFLICT` (its comparison would use the wrong specifications) and
listed for catalog review; if another reason already excludes it, that reason keeps precedence and
the disagreement is still shown. Every row also carries `variation_spec_evidence`: what the variation
itself states for each field and from where. `MATCH_REVIEW` rows never enter the comparison; the
selection audit shows them beside a finding (status, date, whether the review row records the
*current* variation or a stale one, its unresolved note), and a stale row's fields never override the
current selection.

Result on the 2026-11-03 data: of the 62 mapped variations in the pool, one disagrees with its target:
`780290062|21327704634|245580060344` (variation `5:I3-7GEN/4GB/128GB`, target `TGT-000238` records
Core i5; that target also records `cpu_model` "Intel i7", which is why it is already excluded). None of
the 53 selected rows disagrees. The same check on the 10-27 pool (185 mapped rows) finds only that row,
after tuning removed four false positives that came from a parent title filling a field the variation
had stated in a form the reader does not parse. Coverage on the 53 selected rows is limited by how
variations are named: cpu series stated by the variation 22 times (parent 19, ambiguous 2, unknown 10),
screen 12 (parent 32), ram 2 (parent 6, ambiguous 38), storage 11 (parent 5, ambiguous 34); unstated
fields cannot reveal a disagreement. `MATCH_REVIEW` has a row for 16 selected rows (all describe the
current variation) and none for 37.

## Reusing earlier discovery

Discovery writes its index files (`search_requests.csv`, `product_inspections.csv`) only at the end of
a round, so a run stopped early leaves unindexed `evidence/` that cannot be replayed (the cancelled
run `20261103T053445Z` is such a run; nothing there is reusable and nothing was deleted). A finished run
can be replayed with `discover_products.py --search-cache <folder> --cache-max-age-hours 24`: its saved
searches and product-page inspections are answered without a request. Today's published run
(`20261103T023824Z/discovery`) already holds up to 235 of the 510 planned search URLs of the 40-context
list and 53 inspections. `run_variation_week.sh` passes it automatically (newest other run with index
files; `SEARCH_CACHE=none` disables it). Observations stay in the history store, which was not touched.
